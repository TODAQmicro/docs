## What personas are

A **persona** is an identity your Qatom account owns, anchored to one of your twins: a membership, a ticket type, a fan club. It can issue **passes** to shoppers. Each pass lands in the shopper's Qatom wallet, and records:

- an **issue number**, which counts up as you issue passes, so you can tell the first fan from the hundredth,
- an **expiry**, one year out unless you choose another date (at most five years), and
- optionally the shopper's name and email.

The API calls an issued pass a **delegate**, and the routes that issue them live under `/v4/persona/{hash}/delegate`.

Passes answer the question "has this shopper paid for access to X?" without asking them to pay again. Because the pass is in their wallet, not in your session or cookies, it stays with them across devices and visits, for as long as it is valid. Typical uses:

- **Memberships and subscriptions**: issue a pass with each payment, and let members back in by checking for it.
- **Unlocking content**: articles, downloads or features for holders only.
- **Tiers**: the issue number range decides who gets in, so the first 100 holders can see something the rest cannot.

## The flow

1. The shopper **pays** for an item with the [payment element](/reference/payment-js/payment-element/). Your page receives a `payment` event with the payment's `nonce`, `timestamp` and the shopper's wallet `hostname`.
2. Your page sends those to **your server**, which confirms the payment with Qatom and then **issues a pass** from your persona to that wallet. This needs your account's credentials, so it never happens in the browser.
3. Later, on any page, the shopper presses a **verify element**. They sign in, and Qatom checks their wallet for a pass from your persona. Your page receives `verified` or `unverified`.

You need a persona anchored to a twin your account manages. `POST /v4/persona` registers one; see the [API reference](/).

## Issue a pass after a payment

Your server makes three calls, all with your account's access token. Keep the client pair and the token on the server; never put them in a page.

**1. Get an access token** with your account's client pair. A token lasts an hour, and asking again while it has more than five minutes left returns the same one.

```bash
curl -X POST "https://pay.m.todaq.net/v4/account/oauth/token" \
  -u "<CLIENT_ID>:<CLIENT_SECRET>"
```

**2. Redeem the payment**, with the item's hash and the `nonce` and `timestamp` from the `payment` event. A `200` means it was a real payment and is now used, so it cannot earn a second pass. A `400` means no unused payment matches: do not issue.

```bash
curl -X POST "https://pay.m.todaq.net/v4/payment/$HASH/validate" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d "{\"nonce\": \"$NONCE\", \"timestamp\": $TIMESTAMP}"
```

**3. Issue the pass** to the shopper's wallet `hostname`. `name`, `email` and `expiry` (an ISO 8601 date-time) are optional.

```bash
curl -X POST "https://pay.m.todaq.net/v4/persona/$PERSONA_HASH/delegate" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d "{\"hostname\": \"$SHOPPER_HOSTNAME\"}"
```

A `204` means the pass was issued. A `404` means the persona is not one your account manages, and a `502` that the shopper's or your twin failed; the payment is already redeemed, so retry the issue rather than asking the shopper to pay again.

The same, as a server route in Node 18 or later:

```javascript
const API = "https://pay.m.todaq.net";

// Your persona. Keep it on the server, so a page cannot ask for another one.
const PERSONA_HASH = "<PERSONA_HASH>";

async function accessToken() {
  const credentials = Buffer.from(
    `${process.env.QATOM_CLIENT_ID}:${process.env.QATOM_CLIENT_SECRET}`,
  ).toString("base64");

  const response = await fetch(`${API}/v4/account/oauth/token`, {
    method: "POST",
    headers: { Authorization: `Basic ${credentials}` },
  });
  if (!response.ok) throw new Error(`token: ${response.status}`);
  return (await response.json()).access_token;
}

// Called with what the page received in its `payment` event.
export async function issuePass({ hash, nonce, timestamp, hostname }) {
  const token = await accessToken();
  const headers = {
    Authorization: `Bearer ${token}`,
    "Content-Type": "application/json",
  };

  const redeemed = await fetch(`${API}/v4/payment/${hash}/validate`, {
    method: "POST",
    headers,
    body: JSON.stringify({ nonce, timestamp }),
  });
  if (!redeemed.ok) return false; // Not a payment, or already used.

  const issued = await fetch(`${API}/v4/persona/${PERSONA_HASH}/delegate`, {
    method: "POST",
    headers,
    body: JSON.stringify({ hostname }),
  });
  if (!issued.ok) throw new Error(`issue: ${issued.status}`); // Retry later.
  return true;
}
```

Redeeming proves that someone paid for the item. The `hostname` comes from the shopper's page, so check that the item is one that should earn this persona's pass, and do not accept a persona hash from the page.

The signup demo below runs on this site's own route, `/api/delegate`, which does the same with [payment-node](/reference/payment-node/usage/) 0.3.6 (`apiVersion: "v2"`). That release still calls the older v2 and v3 routes, and writes your client secret and tokens to `console.log`; new integrations should call the v4 routes above.

## Check for a pass in the browser

On the page that should be for holders only, mount a [verify element](/reference/payment-js/verify-element/) for your persona, with the range of issue numbers that may enter:

```html
<div id="verify"></div>

<script type="module">
  import "https://cdn.m.todaq.net/micropay.js";

  const micro = await loadMicroPayments("<PUBLIC_SECRET>", { apiVersion: "main" });

  const element = await micro.elements().create("verify", {
    hash: "<PERSONA_HASH>",
    issueMin: 1,
    issueMax: 10000,
  });

  if (element) {
    element.mount("#verify");
  }

  document.addEventListener("verified", () => {
    // Show the holders' parts of the page.
  });
</script>
```

Set `issueMax`: without it, only issue number 1 passes. The `verified` event is for your page, not proof your server can rely on; the [verify element reference](/reference/payment-js/verify-element/#checking-the-result-on-your-server) covers checking on the server, every option and the events.

## Examples

These run against production with a demo account. Press the buttons to see each step, but do not complete a payment or submit the form.

### Sign up, pay and receive a pass

A form takes the shopper's name and email, and a payment element sells a membership. When the `payment` event arrives, the page posts the payment and the form fields to `/api/delegate`, which redeems the payment and issues the pass to the shopper's wallet, recording their name and email on it. The page then shows a verify element for the same persona.

### Verify by issue number

### Verify before buying

A verify element in front of an item for holders only. The item's payment button is drawn transparent, so the shopper sees only Verify; when the verify element reports success (the demo listens for `verify`, which fires with `verified`), the page opens that payment button's checkout. To open checkout, the demo posts a message into the payment element's iframe, which is not part of payment-js's API, so do not copy that part. As with any event, a script on the page could dispatch `verified` itself, so this keeps casual visitors out rather than enforcing access.
